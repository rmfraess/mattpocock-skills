# Test-Driven Development for Games

For direct Unreal PCG element fixtures, provide real owner bounds before registering the component, set explicit on-demand generation and disable editor regeneration, and initialize the context's execution time allowance: `AsyncState.EndTime` defaults to zero, so one `Execute` call can stop between phases before the behavior is exercised. Bound any continuation loop.

For generated dynamic-mesh checks, inspect the target engine's `FDynamicMesh3::CheckValidity` signature: its default failure mode can assert and terminate the Editor. Use its nonfatal reporting mode to turn invalid topology into an ordinary failed test, while still requiring validity; do not weaken topology acceptance or credit a crash as behavioral red. Separate upward orientation (`normal.Z > 0`) from an approved maximum slope: a near-horizontal normal threshold also rejects legitimate rounded shoulders. Define the slope contract before the trial and diagnose failures without silently loosening it. Measure crown-to-edge shape and representative actual-component collision separately; peak depth, short boundary edges and valid topology cannot establish rounded appearance or scene-wide collision. For clipped scalar-field surfaces, count disconnected vertex fans and use native `FDynamicMeshEditor::SplitBowties` when needed, then require strict validity. Diagnose tiny-face collision failures with actual coordinates and minimum altitude: physics cooking can discard submillimetre slivers despite mathematical validity. Repair shared crossings consistently and test every emitted fixture face; do not skip failed probes or infer a regional collision pass from a local repair. Test upward shading overlays separately from top-down collision, and explicitly calculate DynamicMeshComponent tangents if no tangent attributes exist. Compare persisted oriented face coordinates rather than raw vertex IDs/gaps: serialization can compact them without changing geometry. Encode authored geometry digests in explicit numeric storage (such as float64 XYZ plus int32 triangle indices), not raw JSON numbers: native JSON may write 0 where Python readback writes 0.0. Verify numeric equality before diagnosing persistence corruption. For boundary-derived mound trials, test crown curvature and a lower joined saddle independently: a capped smoothstep can flatten the summit, while unrestricted smoothing can erase the saddle. Preserve footprint and support separately; these prototype checks do not establish regional integration. For chunked terrain cover, shape and compute normals before partitioning so storage borders do not become false melt boundaries. Compare normals on actual shared edges, not coincident disconnected fans; normalize readback to the overlay's stored float32 precision before declaring a seam. Retain global geometry, per-face collision and region-size checks because a small approved prototype can read differently on large forest patches.

For deferred Editor-capture recovery, inject a startup failure after callback registration as well as mid-capture, restoration and report-write failures. Assert that the caller sees the error with no callback left able to change the scene; finish-only tests do not cover setup. Keep offline fake fixtures distinct from native fault-path replay.

For native-engine fixtures, establish valid engine-owned storage before testing behavior; a fixture crash is not a behavioral red. Validate dimensions, layer identity and backing allocations before indexing native arrays. For Landscape import, paint replacement or Undo/Redo tests, follow [Landscape fixtures](references/landscape-fixtures.md).

TDD is red, green, refactor. Use this reference to keep tests valuable: what a good test is, where it belongs, common anti-patterns, and the rules of the loop. Apply the guidance on every cycle.

When exploring the codebase, read `GLOSSARY.md` if it exists so test names and interface vocabulary match the project, and respect relevant ADRs.

## Good tests and seams

Test behavior through public interfaces, except for explicitly required storage verification at an agreed seam. Tests should read like a specification and survive internal refactors. See [tests.md](tests.md) for examples and [mocking.md](mocking.md) for mocking guidance.

Use project-approved testing guidance supplied by the caller together with the conversation, spec, and ticket. Reuse agreed seams without asking for another confirmation. If no seam is agreed, or a materially different seam is needed, explain why and ask before writing that test.

For each proposed seam, give a one-line note on what it catches and misses, including any engine interaction or saved-content behavior that requires a separate check.

For stateful correction tests, exercise the real transition path when it exists; if direct storage seeding is necessary, label that seam rather than claiming to test the correction API. Retain actual before/after review and binding records and assert their independently captured IDs and values: serializing metadata and replaying it unchanged cannot detect a wrong saved binding. For timing corrections, hold fact/evidence identity constant while changing both native point and time qualification; assert the full current observation tuple and the independently captured raw history. Exercise the first valid alignment after correction as well as repeated alignment: a renewal-only regression can miss a collision between historical and corrected source rows. Cover withdrawal → source reimport → restoration → renewal, and pair accepted-result checks with pending/unresolved discovery checks so a shared filter cannot fix stale positives by hiding legitimate leads. For provenance guards, test the derivative's own reviewer and payload hash, then substitute a different valid source-ID/hash pair and recompute the derivative hash; a stale-hash failure alone does not prove that the original source supports the association. Also remove lineage fields while retaining derivative-only content and recompute the hash: a derived record must not become direct approval merely by falling through a default branch. Exercise the real writer with lineage fields and assert either exact preservation or explicit pre-write rejection, because a hand-seeded valid read fixture cannot prove the writer accepts that format.

For named-reviewer and substantive-basis rules, test spaces, tabs, newlines and non-breaking spaces on both writes and persisted reads, including support, association and interval consumers. Reuse one Unicode-aware predicate such as a string type check plus `bool(value.strip())`; SQLite's one-argument `trim` only removes ordinary spaces, so it is not an equivalent read guard. For read-boundary fixtures, inspect storage constraints first and use domain-invalid values the unchanged schema actually permits; a CHECK rejection is a storage guard result, not a red test of the reader. Restore valid metadata and verify the positive result, and assert invalid writer calls leave all affected tables unchanged.

When the shape of an interface or test seam is itself in question, first confirm the adapted `gd-codebase-design` package is available, then load it with the available Skill tool and consult it as a reference. If it is unavailable, report the missing dependency and do not substitute the original `codebase-design` guidance.

## Anti-patterns

- **Implementation-coupled:** tests private methods, internal collaborators, or incidental details. Prefer public behavior. A required persistence check at an agreed seam is not implementation-coupled when it asserts only the required contract.
- **Tautological:** the expected value restates the implementation and cannot disagree with it. Use an independent literal, worked example, or spec requirement. For authored data and imports, assert domain requirements independently on the persisted statement, key/predicate and value; comparing a row only with its payload proves serialization, and both can agree on the same scope error. Keep round-trip/hash checks separate from this semantic oracle. For guard tests, give each guarded call otherwise-valid inputs, invoke and assert each independently rather than short-circuiting them, and include an allowed-path control; an unrelated validation failure or a resolver that always rejects can otherwise pass. When rejecting ambiguous identifiers, also test existence checks and creation/import callers, which must not mistake ambiguity for absence. For spatial noise, exercise the actual default seed as well as an art seed: large seed offsets can collapse local variation when the engine casts coordinates to float; bounded periodic offsets preserve spatial detail. Visual coverage assertions must reflect the user's patch/negative-space requirement rather than reward maximum coverage.
- **Horizontal slicing:** writing all tests before implementation commits to imagined behavior. Work in vertical slices, where each test informs one minimal implementation.

## Rules of the loop

- **Red before green.** Write and execute the smallest regression against the old behavior; require the intended behavioral failure rather than a fixture, compile or access failure. When adding coverage for an existing guard, temporarily disable that guard or inject the specific unwanted mutation in a disposable copy and require the new assertion to fail, then restore the real implementation and require it to pass. Then make the minimum implementation change and execute the same regression again. When a fixture dynamically loads the implementation, mutate the module instance that fixture actually exercises; changing a separate in-memory import does not test the guard. A test written before the fix but never run is not a red phase. Identify which layer failed: an offline evidence/coverage guard proves that artifact criterion, not execution of new generator behavior. Before reusing a task-local acceptance helper, inspect its captured baseline paths and normalize native structs through the same serialization used by the saved baseline; an obsolete snapshot or tuple/list mismatch is an oracle failure, not a content regression. Diagnose and repair the oracle without consuming another authoring trial or resetting expected values to unexplained output. If execution is blocked, label the test unexecuted and preserve the baseline for a later comparison; do not claim TDD or a verified fix.
- **One slice at a time.** Use one agreed seam and one minimal behavior change per cycle.
- **Never refactor while red.** Reach green first, then consider useful refactoring and rerun tests after each refactor.

Use the smallest faithful public interface for pure rules. When the claim depends on actual engine interaction, retain the relevant engine integration check. For tests involving the live Editor, saved maps or assets, or references, read the relevant sections of [GAME-DEVELOPMENT.md](../GAME-DEVELOPMENT.md) and coordinate through the assigned Editor owner. This skill does not authorize Editor operations. Unit or behavior evidence does not establish visual quality or game feel; record those separately through the appropriate human assessment.
