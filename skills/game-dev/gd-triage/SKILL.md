# Game-development triage

Move incoming issues on the project's configured tracker through the existing triage state machine. If the tracker configuration treats external pull or merge requests as a request surface, triage them with the same roles and states. Resolve bare issue numbers according to the tracker configuration.

Every comment or issue posted during triage must start with:

```markdown
> *This was generated by AI during triage.*
```

## Guides

- [AGENT-BRIEF.md](./AGENT-BRIEF.md): write durable, testable briefs, including verified native-content targets when relevant.
- [OUT-OF-SCOPE.md](./OUT-OF-SCOPE.md): preserve the existing method for recording rejected enhancements.
- [GAME-DEVELOPMENT.md](../GAME-DEVELOPMENT.md): read the relevant common rules before Editor-dependent checks or game-content claims.

## Roles and state machine

Two category roles:

- `bug`: something is broken.
- `enhancement`: a new feature or improvement.

Five state roles, unchanged:

- `needs-triage`: maintainer needs to evaluate.
- `needs-info`: waiting on the reporter for more information.
- `ready-for-agent`: sufficiently specified for agent work.
- `ready-for-human`: requires human implementation or unresolved human judgment.
- `wontfix`: will not be actioned.

For a PR, `ready-for-agent` means an agent should take the next step on the diff; `ready-for-human` means it is ready for a human to merge. Each item has exactly one category role and one state role. If existing state roles conflict, flag the conflict and ask the maintainer before changing it.

These are canonical roles, not necessarily the tracker's literal label strings. Read the project's actual mapping in `docs/agents/triage-labels.md`. If the mapping is missing, point the user to the combined `gd-setup-matt-pocock-skills` workflow. Never invent, create, or substitute a label. An agent-ready label is not an Editor reservation or new approval.

Normal transitions: an unlabeled item goes to `needs-triage`; from there it may move to `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`. `needs-info` returns to `needs-triage` after reporter activity. The maintainer may override at any time; flag an unusual transition and follow their direction. A busy shared Editor is not missing reporter information and is not a reason to invent a new state. Record a real resource wait in the existing issue context and apply only the configured role whose meaning fits.

## Invocation

The maintainer invokes this skill and describes what they want. Examples:

- "Show me anything that needs my attention."
- "Let's look at #42."
- "Move #42 to ready-for-agent."
- "What's ready for agents to pick up?"

Triage is for incoming issues or requests, not tickets already produced by a planning workflow.

## Show what needs attention

Query the configured tracker and present these buckets, oldest first:

1. Unlabeled items.
2. Items in `needs-triage`.
3. Items in `needs-info` with reporter activity since the last triage notes.

When external PRs are in scope, include them and mark each result `[PR]` or `[issue]`. Apply the tracker's external-author filter for discovery only; an explicitly named PR is in scope regardless of author. Show counts and a one-line summary per item, then let the maintainer pick.

## Triage one issue or PR

1. **Gather context.** Read the full item, comments, labels, author and dates; for a PR, read its diff too. Reuse prior triage notes and do not repeat resolved questions. Read the project's domain guidance and relevant ADRs. Check for an existing implementation by domain concept, not only the report's wording, and read `.out-of-scope/*.md` for similar rejected enhancements.

   For native game content, identify the reported map, asset, or other target when available, along with starting conditions and the saved or observed result. Search the relevant saved content and references when that is the appropriate check. A code class or generic asset type existing somewhere does not prove that this particular saved result is implemented. Report where you looked and what evidence supports the conclusion.

2. **Recommend.** Tell the maintainer the category and state recommendation, why, and the relevant code or content findings, including whether the request appears already implemented. Wait for the maintainer's direction before making a transition.

3. **Verify the claim.** For bugs, use the smallest faithful reproduction or inspection that can confirm the reported behavior. For PRs, verify that the actual diff supports its claims and run only relevant checks that fit the existing task scope. State whether the claim is confirmed, failed, or still lacks enough evidence.

   If Editor-dependent inspection or reproduction is needed, first establish the connected Editor's actual project and checkout, relevant target, current unsaved state, and the assigned exclusive owner. Keep that owner through inspect, change if authorized, save, and verification. A worker's Git worktree does not redirect the running Editor. Do not mutate a live project merely to finish triage. If ownership, scope, or access is unavailable, leave that check unverified and coordinate through the existing project process.

   A game-project PR checkout or asset check must respect the actual active checkout and unrelated unsaved work. Do not switch the live Editor to a different checkout or claim that a branch diff proves saved native content. If the required check cannot be done within the current authorization and ownership, say what remains unverified.

4. **Grill only if needed.** If missing product or reporter decisions need discussion, load the unchanged `grilling` helper and the available `gd-domain-modeling` skill separately through the current skill-loading tool, one skill per call, then follow their methods. Verify each is available first. Do not silently substitute the original domain-modeling route or run a separate setup skill. Point genuinely missing repo configuration to the combined `gd-setup-matt-pocock-skills` flow.

5. **Apply the outcome.** Use the exact configured strings for the chosen category and state. Remove obsolete category/state labels as needed, preserve unrelated labels, and never create or substitute a label. If a required mapping or label is missing, stop that transition and report it incomplete. For `wontfix`, apply its mapped label before closing.
   - `ready-for-agent`: post an agent brief using [AGENT-BRIEF.md](./AGENT-BRIEF.md).
   - `ready-for-human`: use the same brief structure and state the specific human implementation or judgment needed. A later human creative acceptance step alone does not make otherwise agreed, bounded agent work impossible; state the agent's deliverable and stopping point. A resource wait is not a reporter-information gap or a new readiness label.
   - `needs-info`: post the notes template below with specific, actionable questions.
   - `wontfix`: close with the right explanation. If already implemented, point to verified code or saved content and do not write to the out-of-scope knowledge base. For a rejected bug, explain and close. For a rejected enhancement, follow [OUT-OF-SCOPE.md](./OUT-OF-SCOPE.md), link the record in a comment, then close.
   - `needs-triage`: apply the state; add a comment only when useful.

6. **Read back and verify.** Fetch the item after updates. Confirm exactly one mapped category label and the intended mapped state label, required comments with the disclaimer, and the expected open/closed status. If an operation failed or readback differs, report the incomplete action.

## Quick state override

If the maintainer directly says "move #42 to ready-for-agent", trust the stated override and apply that role. Confirm the specific label changes and any comment or close action, then act. Skip grilling. If no brief exists, ask whether the maintainer wants one.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- specific question 1
- specific question 2
```

Capture resolved facts in "established so far". Questions must be specific and actionable, not "please provide more info".

## Resume prior triage

Read prior notes, check whether the reporter answered outstanding questions, and present the updated picture before continuing. Do not re-ask resolved questions.
