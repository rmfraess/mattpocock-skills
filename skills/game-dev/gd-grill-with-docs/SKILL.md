Load and follow `grilling`, then `gd-domain-modeling`, through separate calls with the host's skill-loading capability. Verify the GD helper is available first. If it is missing, use `grilling` for discussion, skip game-domain documentation updates, and report the missing dependency. Do not substitute base `domain-modeling`.

Read the supplied references, project direction, and task breakdown before asking questions. Resolve intended final playable extent separately from first-milestone coverage and viewing detail; ask which areas need traversal versus cinematic representation only when the user has not already settled it. Preserve connected composition without assuming every area needs close-up or traversable detail. Apply an explicit user clarification such as road-focused traversal rather than defending broader wording left in an old document; detail priorities do not themselves specify movement barriers, a camera mode or smaller regional coverage. Ask only about material unresolved decisions. Reuse settled direction; a clear clarification needs no new interview round. `grilling` owns question rounds, user decisions, and background fact gathering.

For research-database interviews, establish the consumer's desired fact queries and readable outputs before debating schema or passage granularity. Treat requests to comb text as contextual coverage goals, not literal display-line requirements; when reusable facts are the goal, passage storage and tagging are intermediate aids. Explain unfamiliar storage choices with compact examples grounded in read-only existing records, clearly separating actual IDs/statuses from illustrative rows and fresh verification. After accepting queries, check that the proposed pilot can exercise their scope: a chapter sample cannot validate a whole-book change history. Keep the pilot and eventual corpus explicitly separate.

For work that extracts, studies or derives from another party's game or assets (reverse engineering, datamining, adaptation references), first inspect the installed target read-only (folder layout, version manifest, executable hash, archive and extension inventory, engine class/string scan). Dispatch one prior-art research subagent in parallel; it writes its report to a scratch file. Make the downstream-use question the root of round one: reference-only study and re-authoring, private stand-ins replaced before sharing, or shipping extracted content. Refuse to plan toward shipping extracted content. Correct any governing doc wording implying the user can authorize redistributing third-party IP, because only the rights holder can. Also correct a live-client gate worded for online play ("a client connected to official servers") when the target is single-player, so attaching to or instrumenting any running client still needs per-task authorization. If the prior-art report is still running, ask the rest of round one now and add the ToS question when the report quotes the clauses. When the prior art surfaces a ToS clause against reverse engineering, put risk acceptance to the user as their own decision; record it in the Direction section of AGENTS.md together with its basis (personal, non-commercial, unpublished). Then ask about output format and consumer, content scope, runtime-behaviour scope, which variant to target first, ground-truth evidence (normal-play recordings, not instrumentation), tool reuse versus clean-room, a hash-pinned snapshot of the client, and tracking (a wayfinder map for discovery-heavy work). When the user agrees to a recommendation phrased "do X now", that authorizes X; do it, and do not re-ask. When later evidence disproves an assumption the user agreed to (for example a shared retargeted clip set), fix the glossary term and the Direction text in place and tell the user.

When the user asks for real-world references or names an appearance gap, gather the facts before the first question round and show them in it: curated dated photos (see the `research` skill's photo-reference recipe), the physical processes that cause the features, the current scene's evidence image, and an inventory of owned and installed assets relevant to the gap. Then ask only the decisions those facts open up, such as which ingredients to use, where assets come from (reuse owned, check the user's library, or acquire new under a new licence), the scale or amplitude as concrete numeric options, the mechanism, the effects on accepted work, and scope and records. For the size of distant landforms, give the options as angular height above the horizon from the canon viewpoint, each paired with a real-world view of that size. Canon and approved images constrain apparent size, not metres, and the same height reads very differently at 6 km and at 20 km. Before offering any numeric option, check it against the other constraints already agreed or proposed in the round, with a cheap offline prototype where one exists. For example, a uniform real-terrain scale must still give the required relief inside the available band at the agreed apparent size. Present an option that cannot hold together with them with that tradeoff stated, never as compatible. Filter reference ingredients against source canon, for example no spring flowers in a failed spring, and label photos as reference, not canon. Before searching externally for assets or references, check the project's research repo for earlier candidate boards and reference documents, and reuse their findings.

For environment or procedural mechanism questions (for example whether terrain relief should run inside the vegetation Generate), measure the representational limits first, such as Landscape grid spacing in each area. State them in what the user sees: how many pixels one grid cell covers at each acceptance view's distance, the height headroom, and how far the feature is from the Landscape edge (method in `ue-landscape-and-foliage` `references/terrain-realism-benchmark.md`). Then present the options against the **eventual** coverage extent, not only the current test tile, because the user judges mechanisms by whether they scale across the map. When a feature spans scales the representation cannot carry everywhere, split it by scale. For example, relief smaller than a few grid cells goes in Generate as placed meshes, and broad relief is saved as a deterministic world-position terrain layer. Calculating from world position lets new areas join up seamlessly. Do not let one generation pass both write Landscape heights and sample them unless it waits for the Landscape to be ready, because the engine applies Landscape edits in the background and samples taken in the same pass read the old heights. Name finer-terrain expansion as a separate, later approval decision.

Treat a generated task breakdown's session boundaries, approval gates, prototypes, and benchmark cadence as proposals unless the user adopts them. When the user wants forward momentum, favor integrated build-and-review milestones with the smallest claim-specific checks; retain ownership, persistence, and safety checks rather than replacing them with process rituals. If a consequential feel or appearance question actually needs an experiment, name the question and smallest useful playable or visual test, then route to `gd-prototype` only when available. If it is missing, report that experiment route as blocked instead of substituting another workflow. Discussion does not authorize Editor mutations; use existing authorization or hand off for the user's choice.

Record approved terms and decisions with useful reference or evidence pointers in existing project docs. When the user accepts a shown asset set or promotes an image to visual authority, record acceptance of that exact appearance and remove current pending-status language; preserve the original image bytes and historical evidence. Keep source canon, technical readiness and full task acceptance distinct, because approval of silhouettes does not verify placement, wind, collision or performance.

When asked to review docs and issues against the build, gather facts before the first round with parallel read-only subagents: issues versus commit history, docs versus source/scripts/config, and a build inventory (maps and default maps, scripts and whether anything references them, untracked content, dirty submodules). Have each write its report to a scratch file. Run `git status` at the start and again after the audits, because another session's Editor work can save a map mid-review; report such changes as another owner's, not yours. Then grill on the authority split this user holds: the build (code, assets, config) states current behavior and values, so docs carry only what the build cannot (intent, canon versus interpretation, references, rejected options); issues carry remaining work, dependencies and acceptance, linking to the intent instead of copying recipes, parameters or status; evidence files are dated history that the user prefers deleted once the build codifies their results (git keeps them; commit-pinned links survive); `LESSONS.md` is an inbox whose entries get promoted to the place that prevents recurrence (code guard, then plugin, then skill, then AGENTS/SOUL) and deleted, not a permanent store. When an accepted feature already exists in the build, propose deleting the doc text that restates it while keeping the constraints the build cannot show, such as canon limits and rejected options. Prefer making the build answer a question (for example setting default maps in config) over documenting the answer. Delete superseded scripts and docs instead of labelling them historical, because git keeps the history and a dead file still misleads; before deleting, grep for references outside history and evidence, including `import`/`runpy.run_path` callers in other scripts. A script that the docs say must never be run can still be a library other checkers import. Before you promise its deletion, map the whole importer chain (direct and transitive) and offer the options: delete only the script and break its importers; delete the script plus every checker that depends on it; or also delete the other old checkers nothing imports. Recommend the widest cut when the chain only checks past saved states rather than current work, because git keeps the history. Strike through any open guard-issue items that pointed at deleted scripts. When the user's reason for a cleanup states a fact about a map (for example "the road isn't in the map any more"), check the live map before acting on it: a feature removed from the test-bench tile can still exist in the game map. Correct the fact and keep the decision if it still holds. When a name misleads, for example a map named after one scene in it, measure the rename's footprint first: the package count, prefixed asset names, script and C++ references, and LFS rules. This user wants a full rename, not a partial one, because every leftover artifact keeps misleading: asset folder, maps, asset names (drop old project/task-code prefixes and keep only Unreal's type prefix, adding a descriptive word only on a clash), actor labels, scripts, C++ paths, config and LFS rules. Exclude only external research repos whose name is still correct. Recommend doing it as soon as the Editor is free and no other session is mid-feature, because every new asset adds to the cost. Before renaming, offer to delete dead content (old proof maps whose packages nothing outside their folders references, and evidence docs the build codifies) so it is not renamed for nothing. Triage a large LESSONS inbox with a subagent that returns one row per entry (delete / promote to an exact destination / keep, with a cited reason), and spot-check its "already covered" claims before presenting them. Apply the agreed cleanup this way:
- Promote into skills as one imperative rule plus the mechanism, under an existing topical heading or reference file; drop trial values and measurements, which the scripts and commits already hold.
- Turn code-guard and plugin promotions into issues, one per destination, each item linking the entry at a pinned commit SHA, then delete the entries. Before planning plugin issues, check `gh repo view <owner>/<repo> --json hasIssuesEnabled,isFork`, because forks often have Issues disabled. First check the project's label mapping for a plugin label, which means plugin fixes are tracked in the game repo. Otherwise recommend a game-repo issue per plugin with a `plugin` label, because this user tracks everything in one project.
- Delete entries by matching their text, and after the edit compare the kept set against the original file at the pinned commit. Another session may commit to the same checkout mid-task, which shifts line numbers, and a check that each deleted line is "a Gotcha line" will not catch the shift.
- When renaming or deleting a doc, rewrite links in every referring file, including the evidence files, and remap their `#section` anchors to the new headings.
- Re-run `git status` and `git log origin/main -3` before committing, because the other session may have committed and pushed in between. Stage only the files you own.

When a clarification changes governing scope, reconcile records in order: read current project direction and relevant parent/child task bodies; update conflicting current requirements while preserving unrelated scope and acceptance checks; read back exact remote bodies and unchanged task states. Treat the clarified intent as controlling instead of adding a contradictory comment beneath stale requirements. Keep accepted project decisions in project records rather than portable skills. Mark tentative ideas as assumptions, and create no document for every choice. Keep the glossary to project terms the build and docs still use. Leave out canon names the books define, and drop a term as soon as its reference is no longer used. For relevant Unreal project, Editor, map, asset, saving, or acceptance rules, read [GAME-DEVELOPMENT.md](../GAME-DEVELOPMENT.md).
