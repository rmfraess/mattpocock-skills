# Game Code Review

Use this for a branch, PR, work in progress, or a request to review "since X". Review has two independent axes:

- **Standards:** does the change follow this repository's documented standards?
- **Spec:** does it implement the originating issue or spec?

Run the Standards and Spec reviews in parallel when bounded read-only delegation is permitted, then aggregate their findings. Otherwise perform both axes directly and label self-review honestly. For reviews involving maps, assets, saved results, Editor ownership, or game-feel evidence, read the relevant sections of [GAME-DEVELOPMENT.md](../GAME-DEVELOPMENT.md). Load issue-tracker instructions only when resolving an issue or changing tracked state; an absent tracker document must not block a self-contained review-and-commit request.

For a review-and-publish request, own the authorized sequence: validate usefulness, fix verified findings, commit the exact reviewed files, push only when separately authorized, and read back the result. For a commit/push-only follow-up to an already reviewed result, reuse acceptance and claim-specific test evidence while its inputs remain unchanged; refresh the pending inventory, relevant Editor dirty/saved-state gate, staged representation and remote state rather than reopening visual iteration or repeating cleanup. When a request names one change, commit only its explicit paths; if pushing the branch would include earlier unpublished commits, show that ahead range and obtain authorization for the additional publication. Once the user authorizes all of that range, fetch again, verify the same outgoing commits and no divergence, then push without another approval round. Treat this as publication of the current branch's verified ahead range, not permission to push unrelated branches or rewrite history. For a host project referencing an unpublished plugin/submodule commit, include the child repository and destination in that same publication decision; after approval, complete every repository's preflight before the first push, then publish and verify the child before its host so the host never advertises an unavailable dependency. Keep the handoff to the new commit, destination, earlier commits included and clean/remaining worktree state.

For pre-commit artifact cleanup, freeze the complete staged, unstaged and untracked inventory; give each retained file a concrete purpose as a scene dependency, maintained tool/input, current acceptance evidence or governing procedure. Check retained validators against the latest representation, not just whether they run offline: earlier migrations can leave checks asserting retired actors, obsolete visibility or old population totals. Retire superseded validators or update the current one without dropping its preservation coverage. Identify the required live verification and resolve any Editor-ownership gate before changing executable check behavior; do not finish cleanup only to discover its new checks cannot be exercised. Trace references before deleting. A prepared dependency with no current scene referencer can still earn retention for the explicitly authorized immediate continuation: name its concrete consumer and purpose, distinguish reservation from active use, and do not retain speculative variants. Remove unreferenced one-off construction/repaint helpers when saved assets are the deliverable and no maintained rebuild/recovery path requires them; keep editable inputs and the smallest runnable check. A useful cleanup may retain every file: remove redundant fields and stale prose rather than inventing a file-deletion target. Preserve the accepted result instead of reopening visual iteration. When the user asks to clean up and commit before continuing a fix, finish that checkpoint first; retain an honest known-defect disposition rather than treating the commit as feature completion or restarting correction. Keep cleanup proportional: update stale check inputs without redesigning the verification system unless a concrete finding requires it. Cleanup authorization alone does not authorize commit/push. Give excluded leftovers an explicit disposition (retain for a named consumer, archive, or request bounded deletion permission) rather than leaving rejected trials unexplained after a checkpoint. For authorized leftover-only cleanup, prefer a clean checkout with verified local recovery over committing rejected assets or adding another tracked cleanup diary.

Keep one concise current index/report and distinct supporting evidence. For folder cleanup, keep established deliverable paths stable and relocate working material through a hash-verified old→new map; inspect actual selection records because an older revision can still contain a selected asset. Preserve hash-registered originals and point current navigation to later state rather than rewriting their status text without versioned provenance. Put the current saved result, reusable check and unresolved blockers ahead of historical trial details; a resolved local defect must not remain described as current elsewhere in the report. Consolidate duplicated expectations, obsolete captures and failed-probe payloads in place while preserving source provenance, accepted scope and required checks; retain an honest limitation instead of an invalid benchmark. Update affected producers and consumers so their next run preserves the cleaned layout. Exercise write-heavy generators in a disposable copy with full preservation-guard coverage; follow the [relocation replay recipe](references/evidence-publication.md#folder-relocation-and-generator-replay), not an in-place rebuild of selected outputs. Prove retained normal checks work without ignored recovery inputs; distinguish those checks from historical replay and live correctness. Keep recovery manifests local, not another committed audit diary. Report cleanup, checks and publication state briefly. For hash-manifest or ZIP handoffs, verify exact-byte companions through Git checkout conversion before calling them commit-ready; worktree-only hashes miss line-ending changes. Use [evidence publication](references/evidence-publication.md) for retention decisions, the exact-byte checkout recipe and the Git sequence.

## Process

### 1. Establish the review scope

Use one of two explicit modes:

- **Committed history:** use the fixed point supplied by the user, such as a commit SHA, branch, tag, `main`, or `HEAD~5`. For an identified PR or remote branch, verify and pin its base and head SHAs; inspect `git diff <base>...<head>` and `git show <head>:<path>` rather than switching a dirty integration checkout. Confirm the objects match remote metadata, and keep worktree-only files out of the review. Report a missing or unresolved base/head rather than guessing. Distinguish a test run on an integration checkout from a build of the exact reviewed branch, even when the changed files match.
- **Implementation scope:** use the starting revision and exact task-owned changed-file and asset inventory supplied by the caller. Cover staged, unstaged, and new files; exclude unrelated work; include tracked-file diffs and complete new-file contents. For non-text maps or assets, also require available semantic, reference, saved-state, runtime, or visual evidence appropriate to the claims. Review the intended outputs, not only the script or text diff that produced them. Do not widen the scope or fall back to committed history. If required material is missing, report it before dispatching reviewers.

For a fork contribution audit, compare each fork branch with its corresponding live upstream target and pin both remote SHAs before reviewing: a local remote-tracking ref can be stale, and comparing a release branch with an unrelated upstream branch misclassifies history. Inspect unique non-merge commits and actual patches, existing PRs and maintainer disposition; ahead counts include merges, and different commits can contain equivalent changes. Separate independent candidates from already-merged, overlapping or explicitly superseded work; do not treat a shared integration branch as one submission. For an authorized focused contribution from a dirty mixed-scope checkout, isolate the reviewed patch on a clean upstream-based branch in an appropriately authorized separate worktree; compare the complete staged inventory and normalized text contents against the tested snapshot before committing, and leave the integration checkout untouched. Before publishing, recheck the upstream base, outgoing commit range and remote branch; after creating the PR, read back its exact head, base and body, including material test limitations. For a conservative guard, identify the concrete built-in and extension workflows it excludes, whether it changes an existing API or limits only a new one, and what state remains unexamined; a native workaround or a class-based allowlist is not proof that external references are safe. Describe user prevalence as unknown unless measured. Report candidates as unverified until current-upstream compatibility, tests and behavior are checked. When asked about deleting a merged contribution branch, verify its current remote tip matches the merged PR head and check for other open PRs; distinguish the contributor's branch from the upstream branch carrying a later integration PR, which does not depend on the fork branch.

For committed history, capture `git diff <base>...<head>` once and list commits with `git log <base>..<head> --oneline`; use `HEAD` only when it is the intended reviewed head. Before continuing, confirm both revisions resolve and the diff is non-empty, or confirm the supplied implementation scope is complete and non-empty. When the user asks whether an untested platform is a realistic risk, inspect the actual diff for platform-specific code, compiler/linker boundaries, API exports and case-sensitive paths; give a proportionate assessment and separate a concrete failure mechanism from the generic possibility of an untested build. Do not present lack of a test as evidence of a likely defect.

Review only the supplied evidence and scope. A necessary live Editor check is coordinated through one assigned Editor owner, who verifies the actual project and checkout and provides the result. Reviewers inspect supplied diffs, inventories, logs, saved-state reports, and captures; they do not take Editor control, mutate content, or authorize a save. Missing or stale evidence is unverified, not a technical pass.

### 2. Identify the spec source

Look for the originating spec in this order:

1. Issue references in commit messages, fetched through the project's issue-tracker workflow.
2. A path supplied by the user.
3. A spec under `docs/`, `specs/`, or `.scratch/` matching the branch or feature.
4. Use the explicit user request and applicable repository rules as the spec when they define the outcome and acceptance sufficiently; do not require a separate ticket or spec file merely to review useful uncommitted work. Ask only for a missing decision that materially changes acceptance. If neither artifacts nor conversation establish requirements, report that limitation rather than inventing a spec.

### 3. Identify standards sources

Search the repository for all documents that describe how code and content should be produced. Include `CODING_STANDARDS.md` and `CONTRIBUTING.md` when present, and read the applicable standards. Apply actual engine and project conventions. Smell suggestions are advisory; do not demand extra abstraction, polymorphism, or a rewrite only to satisfy a generic heuristic. Repository standards override the following smell baseline, and each smell remains a judgement call rather than a hard violation. Skip anything tooling already enforces.

- **Mysterious Name:** a function, variable, or type name does not reveal what it does or holds. Rename it; if no honest name fits, the design may be unclear.
- **Duplicated Code:** the same logic shape appears in multiple hunks or files. Extract the shared shape and call it from each site.
- **Feature Envy:** a method reaches into another object's data more than its own. Consider moving it onto that data.
- **Data Clumps:** the same fields or parameters keep travelling together. Bundle them into a type and pass that.
- **Primitive Obsession:** a primitive or string stands in for a domain concept that deserves a type. Give the concept a small type.
- **Repeated Switches:** the same conditional on the same type recurs. Consider polymorphism or one shared map.
- **Shotgun Surgery:** one logical change forces scattered edits. Gather the related behavior into one module.
- **Divergent Change:** one file or module changes for unrelated reasons. Separate those reasons.
- **Speculative Generality:** abstractions, parameters, or hooks lack a current requirement. Delete them and inline back until a real need exists.
- **Message Chains:** long navigation exposes details callers need not know. Hide the walk behind a method on the first object.
- **Middle Man:** trace what a delegating wrapper contributes before removing it. Keep a minimal boundary that supplies validation, authoritative persistence or otherwise unavailable platform access; remove it only when the direct path demonstrably preserves those guarantees.
- **Refused Bequest:** a subclass or implementer ignores or overrides most inherited behavior. Drop the inheritance in favor of composition.

### 4. Spawn both reviewers in parallel

Issue both reviewer calls together, each with a fresh context window, and collect their returned reports before aggregation. If the host delivers results asynchronously, yield for those results rather than polling or treating dispatch as a completed review.

This is review-only. Neither reviewer edits files, commits, fixes findings, invokes `gd-code-review` recursively, or dispatches more reviewers. Implementers may address verified findings and commit afterward. For read-only Python syntax checks, use `compile(source, filename, 'exec')` or redirect caches to task-local scratch: `py_compile` and `compileall` otherwise create repository `__pycache__` files. Reconcile Git status after reviewers finish, not only before dispatch.

The **Standards** prompt includes the complete supplied scope, standards-source list, and smell baseline above. Ask it to review only the supplied scope, cite each documented standard by file and rule, identify any spotted smell with its relevant hunk, distinguish violations from judgement calls, and stay under 400 words.

The **Spec** prompt includes the complete supplied scope and spec path or contents. For reference-led environments, include the controlling images themselves and matched full-scene/ground evidence; require assessment of regional extent and biome transitions, not only successful local samples or mask hashes. Ask it to report missing or partial requirements, unrequested behavior, and apparently implemented requirements that look wrong, quoting the relevant spec requirement, and stay under 400 words. If the spec is missing, skip this reviewer and say so.

Ask both reviewers to lead with findings (hard violations first, one `file:line: why` line each), then provide stable report/evidence handles so truncation does not hide actionable work. Follow the active delegation tool's completion contract: for notification-driven background reviews, finish independent work and end the turn rather than polling live transcripts or artifact files. After reported completion, inspect the returned report and verify each finding against the frozen scope. If a completed return is truncated, partial or interrupted, preserve it and enumerate the unverified remainder; inspect its full report, finish that bounded remainder directly with honest self-review attribution, or redispatch only the unresolved scope. Treat missing findings as unverified rather than inferring a process failure or claiming the entire review is addressed.

### 5. Aggregate

Verify each finding's location and supporting standard or requirement before confirming it. Recompute any arithmetic a reviewer uses against the raw data, grouped the way the claim groups it: pooling instances of different scale or category into one average can make a correct per-group figure look wrong. Fix the doc wording so it states the grouping, instead of adopting the reviewer's number. Give the Spec reviewer the raw measurement files and each figure's definition (tolerance, nearest-obstacle vs any-obstacle, checker version); otherwise two correct counts with different definitions read as a mismatch. Reproduce suspected checker defects with a small counterexample: sorting a collection of triangles does not sort the vertices inside each triangle, so do not reset an oriented-geometry baseline to fix a misread expression. Distinguish a missing executable guard from a false measurement; retain authentic expectations and add the smallest rejection test plus the appropriate live replay. Reconcile conflicting visual descriptions against the exact current full-resolution capture and a matched baseline crop; a generated sheet can contain a stale shader-warm-up image even when the saved assets are correct. Route recapture through the Editor owner, and distinguish transient fallback from inherited low-contrast texture repetition before approving or requesting a fix. Treat image-analysis commentary as observations about pixels, not authority over intended season/species, task scope or creative approval; discard invented diagnoses or acceptance recommendations. Correct or omit unsupported claims, label claims that cannot be verified, and reconcile each review's finding count. For a review-only report, present findings under `## Standards` and `## Spec` without merging or reranking them. For an authorized review-and-fix or review-and-publish request, resolve verified findings and summarize the actual changes and remaining limitations instead of sending an unrequested full review report.

Add a concise **Execution Evidence** assessment as an aggregation step, not a third reviewer. State what was run and inspected, whether evidence matches the reviewed state, which checks or file edits failed, and which completion claims remain unverified. When a verification job finishes after dispatch, match its runtime/input fingerprints to the frozen inventory and supply its result as an evidence supplement instead of rewriting the manifest or restarting unchanged reviews. Distinguish inspection of supplied test logs from an independent rerun. Trace claimed guards to the actual maintained entry point: an ad hoc assertion or import is not a retained offline regression. For transactional native changes, inspect Undo and Redo coverage for every mutated representation, not just the primary object. Fix verified coverage gaps in place, rerun the affected entry point/build/tests, and bind the final reviewed inventory to those results; avoid another broad review cycle for a small test-only correction. Keep comment-only closure proportional: preserve the actual executed producer bytes/hash, record the amended source separately, and use an existing targeted check or a small diff/AST check to establish that output-relevant logic is unchanged. Never relabel an old execution hash, treat AST equality as universal runtime equivalence, or build a permanent provenance subsystem merely to close a wording finding. After a rejected patch, inspect the exact target and distinguish required work from optional cleanup. Disclose an intentionally skipped edit even when the main deliverable passes; a clean commit does not mean that failed patch landed. Separate technical verification from creative or game-feel acceptance. Attribute a user verdict only when the user supplied it; a favorable reviewer description is not user approval. Mark creative acceptance not applicable when no such decision exists. Assess readiness to commit/push separately from readiness to close the issue. Judge closure against the approved pass: once the creative owner accepts its documented coarse limitations and required technical checks pass, retain those limitations as follow-on work rather than requiring final art, deferred architecture or tests assigned to later tasks. For an approved foundation/final-art split, record the revised boundary explicitly in the existing issue, preserve the earlier rejection as history, and put only the displaced refinements in one follow-on after checking existing tickets for overlap. Verify the unchanged production baseline with current representative views and any missing loading/cost evidence; credit technical criteria separately. Approval of the split or permission to continue is not advance acceptance of newly captured views: request only that remaining visual verdict, then close when authorized and satisfied. Update the current disposition in place; do not keep presenting a resolved acceptance gate as outstanding.

For live-Editor evidence, distinguish the source checkout from the binaries actually loaded. Pin engine/plugin versions and build mode at execution, then recheck checkout and relevant artifact fingerprints at handoff. If another session advances source while installed binaries remain loaded, audit the delta and retain unchanged asset observations against their actual execution environment; do not certify a fresh build of the newer revision or rebuild/revert someone else's work merely to make the SHAs match.

For a bounded visual experiment, classify **test execution** separately from **the desired appearance**. A valid negative experiment can be complete while the art cue remains unmet; technical passes and small pixel differences do not authorize promotion or an automatic next technique.

End a review-only report with findings per axis and the worst issue within each axis, if any; do not select a single winner across axes. End a review-and-publish task with the verified commit/remote branch, useful cleanup performed, and any remaining blocker; keep routine successful status brief.
