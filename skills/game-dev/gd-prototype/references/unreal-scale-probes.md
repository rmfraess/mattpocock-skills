# Unreal scale-walk probes

Use when the question is **how large a blockout feels from human height**, before player movement and camera design are approved. A native `DefaultPawn` on a fixed XY plane is a scale-view instrument, **not** a gravity-driven character or a collision/traversal pass.

1. **Reconcile the target.** Confirm exclusive Editor ownership, project/map, dirty packages, engine version, ground height, existing pawns/input/PlayerStarts and saved checkpoint. Read the engine's `DefaultPawn` input bindings or inspect the live class before adding gameplay assets. Its built-in movement and mouse-look bindings can avoid a Blueprint/GameMode/Input Action stack. Do not assume that a project with no PlayerStart has a useful spawn position.
2. **Test native PIE before writing.** Start PIE with `vibeue.exec_tool('EditorToolset.EditorAppToolset','StartPIE')`; the start request is asynchronous, so check `IsPIERunning` in a later call. Obtain the live pawn through `unreal.GameplayStatics.get_player_pawn(unreal.get_editor_subsystem(unreal.UnrealEditorSubsystem).get_game_world(),0)`. If it is a `DefaultPawn`, set its `FloatingPawnMovement` `plane_constraint_axis_setting=unreal.PlaneConstraintAxisSetting.Z`, `plane_constraint_origin` at the chosen eye plane, `constrain_to_plane=True`, and a representative `max_speed`. Teleport near a landmark. Disable collision only when proxy cubes/spheres would invalidate a **scale-only** pass; disclose that choice. Set the controller's control rotation to the intended view and capture the game viewport with `SceneCaptureToolset.CaptureGameViewport`.
3. **Exercise the real input path.** Inject a short W hold with `unreal.InputService.inject_key('W','hold',duration)`; let PIE tick between separate tool calls, then read the live pawn's position. Assert horizontal displacement and stable Z. A Space hold can confirm that the plane constraint prevents upward flying. Do not infer motion from the injection response alone. Release PIE object references before stopping PIE; cached Python references to a torn-down PIE world can crash the Editor.
4. **Persist only if repeatability matters.** Place one clearly labeled `DefaultPawn` in the owned map, set `auto_possess_player=unreal.AutoReceiveInput.PLAYER0`, `add_default_movement_bindings=True`, and the same `FloatingPawnMovement` plane/origin/speed settings. Save only its map package, reload, and read back the actor and settings. Start PIE again and confirm that Player 0 actually possesses **that placed actor**, the keyboard moves it, and Z stays fixed. A placed pawn's actor yaw alone need not determine the initial view: PIE can inherit the Editor viewport's control rotation, so set the Editor viewport camera to the desired pose before Play and verify control rotation on restart.
5. **Hand off honestly.** Stop PIE and restore any background-throttling override; leave the Editor on the saved map. Give novice controls (Play, click the game view, WASD/mouse, Shift+F5) and state exactly what was verified. A no-collision planar `DefaultPawn` may pass through stand-in roads/woods and cannot prove walkable terrain, stepping, jump behavior or final player speed. If those are the question, use a collision/gravity-aware character in a separate prototype instead of relabeling this probe as walking.
